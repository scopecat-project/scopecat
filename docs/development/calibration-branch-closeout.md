# Calibration branch integration

## Delivery boundary

This integration completes recoverable calibration tasks over independent
parameter contexts: retain candidates, compose and verify the final combination,
then publish against the captured destination branch head. It replaces the old
full-configuration cohort orchestration and moves maintained author/teaching
consumers to explicit parameters and executable setup.

The branch also delivers exact scientific-context checks, bounded capability
reports, task controls and diagnostics in the workbench, and scoped dependency
evidence. Dependency observations remain partial and do not enable reuse across
parameter revisions. Full resolved configurations remain valid immutable execution
evidence; remaining legacy editing/working-point consumers are tracked separately.

## Self-review boundaries

- Parameter edits and publication must not silently activate or change setup.
- Candidate consumption identifies exact retained predecessors; final publication
  requires authored combined verification and rejects a changed destination head.
- Task dispatch, adoption and finalization preserve durable identities across
  restart. Scientific rejection and failed prerequisites cannot become acceptance.
- Host preparation evidence is written before its effects under the execution
  lease. It proves neither hardware success nor completed point coverage.
- Analysis configuration access identifies the retained run snapshot, not today's
  parameter head and not every field accessed by arbitrary Python code.
- Schema 98 is a development format, not a compatibility baseline. No historical
  data deletion, migration or old-reader fallback is part of this integration.

## Qualification

The final integration is checked against the ordinary public CI lanes (core,
Python quality, generated contracts, UI and documentation), plus the
[six-target daemon journey](array-maintenance-qualification.md) and current-format
recovery coverage. Record exact commands and outcomes in the PR; individual
commit-level checks are not a substitute for final integration results.

The six-target scenario covers healthy publication, coupled final-verification
rejection, a synthetic prerequisite failure with unaffected progress, concurrent
branch edits, and restart between completed stages. It does not qualify physical
resource contention or interruption during acquisition. Windows human experience
and hardware qualification are deferred to [#616](https://github.com/scopecat-project/scopecat/issues/616).
